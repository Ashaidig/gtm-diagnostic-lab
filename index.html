One question separates the two common causes: open the Data Layer tab of that event and look for the value under any key.

Demo 2 - Which trigger type, and why

ListenersThe click trigger fires sometimes, or not at all

What you were trying to do: track clicks on a call-to-action, a phone number and an email address.

What to watch: Click the coloured circle inside the first button, then click its text. Compare every row of the table. Then click the text inside Book a demo, and the phone and email links.

Show the explanation
Clicking the coloured circle inside the button means the clicked element is the <span>, not the button - so Click ID comes back empty and D2a does not fire, while D2b does, because the CSS selector #cta_quote, #cta_quote * matches the button and everything inside it. That is the single most common reason a click trigger "works sometimes".

On the links: with All Elements, clicking the text inside Book a demo gives an empty Click URL, because the <span> has no href. Just Links resolves to the anchor and gives you the URL every time - which is why phone and email tracking should always use Just Links with Click URL contains tel: or mailto:, never All Elements plus Click Text.

Navigation is prevented here so the page stays put; on a real site, see Demo 4.

Demo 3 - Three forms, three verdicts

ListenersThe form works, but no lead is recorded

What you were trying to do: count qualified leads from the callback form.

What to watch: Submit all three. For each one, decide which of three verdicts it lands on - trackable with a Form Submission trigger, trackable some other way, or not trackable from the container at all. Submit form C twice: once with a valid email, once with an invalid one.

Show the explanation
Three forms, identical to the user, three different verdicts.

Form A. A real form submission, so the browser fires its own submit event and GTM's Form Submission trigger hears it. Verdict: container-only fix, no developer needed.

Form B. There is no <form> element at all - just inputs and a type="button" button in a container. JavaScript takes the click and sends the data itself, so no submit event can exist and the Form Submission trigger has nothing to hear. Form ID and Form Classes will also be empty, which is a second confirmation. But the success message that appears is unique to success and has its own identifier. Verdict: still a container-only fix, using Element Visibility with Observe DOM changes enabled, because the message does not exist when the page loads.

Form C. Same markup as B, except success and validation errors are written into the same message box - only the wording differs. Submit it with an invalid email and watch Element Visibility fire anyway. Verdict: not reliably trackable from the container, because you would be counting failed submissions as leads.

What to ask for on a Form C, in order:
1. A dataLayer event pushed on success only. Best, and unambiguous.
2. Failing that, a distinct element or identifier for the success state. This is often the easier sell - it is a front-end change rather than a tracking change, and it costs a developer about two minutes.
3. Last resort: Element Visibility plus a condition on the message text. Log it as interim - it breaks on a copy change, a translation, or an A/B test, and nobody will tell you when that happens.
Never a click trigger on the button, unless the client has explicitly accepted counting attempts rather than successes.

Note the colour is not a selector. The error state here is red and the success state is green, but both are the same element with the same ID and the same class - the colour is applied inline. Looking different on screen is not the same as being targetable. Judge by the markup, not by the design.

One exception worth checking. Plenty of real sites do give their error state its own class, and if this one did you would be back in case B - target the success element specifically and you are done. Always look at the markup before escalating.

One trap to know about on real sites. If a <form> does exist and it contains a single field, pressing Enter in that field submits it - the browser calls this implicit submission, and it produces a real submit event even when the visible button is type="button". The result is a form that is tracked when people press Enter and untracked when they click. Nobody ever notices, and the numbers are quietly wrong. Always test both ways.

The four-step check that gets you to a verdict, no code required:
1. Inspect the button. Is it type="submit" or type="button", and is there a <form> element above it at all?
2. Submit with Preview open. Did a Form Submit event appear?
3. Submit with the Network tab open. Did anything leave, and what did the server answer? That is evidence for the ticket - you cannot trigger on it.
4. Look at what changed on the page. Is it unique to success, or does the same element show errors too?

What you were trying to do: count clicks on an outbound link that immediately leaves the page.

What to watch: Open the Network tab and tick Preserve log. Click once with the box unticked, come back, then click again with it ticked. Compare the status of the outgoing request each time.

Show the explanation
Unticked: the request the tag sends is still in flight when the browser unloads the page, so it appears in the Network tab as (cancelled) and nothing reaches the platform - while GTM Preview happily records the tag as fired. Ticked: the navigation is held back, the request completes, and the same click is counted.

In the container this is the Wait for Tags option on Click and Form triggers, with a max wait of one to two seconds. On forms, pair it with Check Validation so you do not count submissions the form itself rejects. This is one of the few tracking problems you can fix entirely on your own, in about a minute.

Demo 5 - The popup nobody can see

EnvironmentsIt works on the page but not in the popup

What you were trying to do: count enquiries submitted through the modal that opens on the page.

What to watch: Submit the enquiry, then close the popup and submit a second one. The only evidence a conversion happened is something appearing on screen - work out which trigger reads that, and which of its settings decide whether it fires at all, and whether it fires twice.

Landing page
Popup not opened yet.
Show the explanation
A click trigger on the button counts people who opened the popup, not people who completed anything. The success message is the only honest signal available without a developer, and Element Visibility is the trigger built for reading it.

Two of its settings decide whether it works at all, and both are left wrong constantly.

Observe DOM changes. Off by default. Without it GTM checks for the element once, at page load - and at page load the success message does not exist yet, so the trigger never fires and the tag looks broken for no visible reason. This is the single most common cause of "my Element Visibility trigger does nothing".

Firing frequency. Left on "once per page", the second enquiry in the same session is silently not counted. On a page whose whole purpose is a repeatable popup, that is a permanent undercount nobody notices. Set it to fire every time the element appears.

Third-party popup tools often render their form inside an iframe instead. If the success message is not in your page's DOM, this trigger cannot see it either - that is Demo 6.

Demo 6 - The embedded widget

EnvironmentsThe payment succeeds and nothing is tracked

What you were trying to do: track completed payments made inside the embedded widget.

What to watch: Pay once with the box ticked and once unticked. Each time, watch what reaches the page around the widget.

Payment page
Item B SKU-100290.00
Nothing paid yet.
Show the explanation
An iframe is a separate document. Your container lives on the page around it and cannot see in: no clicks, no form submits, no URL change, nothing.

There are only three ways this is ever solved. One: the widget sends its result out to the parent page and the page pushes it to the dataLayer - the tick box above. Two: you own the content of the iframe and can put a push inside it, which is true for your own subdomains and almost never true for a third-party widget. Three: neither, in which case there is no container-side fix and the answer to the client is that the vendor has to provide it.

Untick the box and pay again: the payment succeeds in front of you and the page around it learns nothing.

Demo 7 - The site that never reloads

EnvironmentsOnly the first page is ever counted

What you were trying to do: count page views across the site.

What to watch: Open the Network tab, filter by Doc, tick Preserve log, then click through the menu. Watch the address bar, and watch the top of Preview’s left rail.

Home

Watch the address bar change while the tab never reloads.

No navigation yet.
Show the explanation
Open the Network tab, filter by Doc, tick Preserve log, and click through the menu: the address changes and no new document is ever requested. That two-minute test is how you identify this on any site, whatever it is built with.

In Preview, Container Loaded, DOM Ready and Window Loaded appear once at the very top and never again, so a pageview tag on any of them counts one view per visit no matter how far the user goes. History Change catches the rest.

With the tick box off you get only the URL change - History Change fires the moment the address updates, before the new content exists, so anything reading the page title or content is reading the previous page. With it on, the site announces the route itself and carries its own data, which is the version to ask developers for. The same lesson applies to values: on a site that never reloads, nothing clears the dataLayer between views, so data pushed for one view survives into the next unless something resets it.

What you were trying to do: count each purchase once, which means every conversion needs a unique order ID.

Two things to notice about the event itself. The site calls it orderComplete, not purchase - event names are not standardised, so never assume one, and never retype one from memory. And it carries no order ID at all.

Without an ID the platform cannot tell a reload, a bookmark or a shared link from a new sale, so the count drifts upward and nobody can explain it. The number is printed on the page in front of you - which means you can read it without anyone's help.

The tag then fires on orderComplete and picks the ID up from the page rather than from the push. Check the outgoing request: it carries an order ID the event never contained.

Build a DOM Element variable with selection method ID and element ID order_number, then map it into the tag's transaction ID field. The GTM Variable Builder extension will generate the selector for you if the element has no ID.

Its limits, which you must say out loud to the client. Scraping breaks the day the site changes, so it is an interim fix with an expiry date, not a solution. And it only works where you can put a container: if the purchase completes on a payment provider's own domain, or there is no confirmation page at all, there is nothing to scrape. In those two cases your options are a return URL carrying the order parameters, the payment provider's own tracking, or a server-side integration - and none of them are container work.
